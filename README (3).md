# LLM-Based Hallucination Detection and Validation for iPhone Product

## 1. Project Overview

This project develops a domain-specific system for detecting and
validating factual claims generated by Large Language Models (LLMs) for
iPhone product information.

The system extracts atomic claims from an LLM response, classifies them
into three knowledge domains, retrieves relevant evidence, validates the
claims using multiple signals, detects source misattribution, and
presents the results through an explainable dashboard.

### Knowledge Domains

1.  **Product Specification**
2.  **Internal Department**
3.  **External Body**

### Core Novelty

> **Domain-aware, claim-level hallucination and source-misattribution
> detection using domain-routed evidence retrieval, NLI, semantic
> similarity, and explainable trust scoring.**

  Backend            Python + FastAPI
  Background Jobs    Celery
  Task Queue         Redis
  Database           MongoDB

  Containerization   Docker Compose
  Communication      REST + WebSocket

### Database Decision

**PostgreSQL is no longer used as the project database.** MongoDB is the
**single database and vector store**. Structured data, document
metadata, operational records, and vectorized evidence are stored in
MongoDB; MongoDB Atlas Vector Search handles semantic retrieval.

## 5. MongoDB Data Model

MongoDB is the single database for the project.

### Core Collections

-   `products`
-   `documents`
-   `product_master`
-   `component_specs`
-   `quality_metrics`
-   `manufacturing_records`
-   `defect_records`
-   `supplier_records`
-   `test_results`
-   `traceability`
-   `claim_evidence`
-   `eval_claims`

### Vector Collections

``` text
spec_chunks
internal_chunks
external_chunks
```

Each vectorized chunk should retain metadata such as `doc_id`,
bucket/domain, department or organization, revision, topic, text, and
embedding.

Planned embedding model: `all-MiniLM-L6-v2` (384 dimensions, cosine
similarity).

-   [ ] Validate `product_id` references during ingestion

-   [ ] Verify record counts after migration
-   [ ] Create required MongoDB indexes

**Important:** MongoDB does not provide relational foreign-key
enforcement in the same way as PostgreSQL. Referential checks therefore
need to be implemented in the ingestion/validation layer.

## 7. Hallucination Detection Pipeline

``` text
LLM Response
    ↓
Atomic Claim Extraction
    ↓
Domain Classification
    ↓
Source Router
    ↓
MongoDB Vector Search
    ↓
Top-K Evidence
    ↓
NLI + Semantic Similarity + Number/Unit/Date Checks
    ↓
Source-Misattribution Detection
    ↓
Supported / Contradicted / Insufficient
    ↓
Trust Score
    ↓
MongoDB Findings
    ↓
React Dashboard
```

### Source-Misattribution Example

Generated claim: \> "QA/QC approved the battery process."

Retrieved evidence: \> Source: Design Engineering

The system should check both **factual support** and **source
attribution**.

## 8. Evaluation Dataset

Create **300--500 labelled claims** with four categories:

1.  `correct`
2.  `wrong_value`
3.  `fabricated`
4.  `misattributed_source`

The test set should be frozen before final tuning.

### Target Metrics

  Component                       Target
  ------------------- ------------------
  Domain classifier      Macro F1 ≥ 0.85
  Retrieval              Recall@5 ≥ 0.90
  Detection             Precision ≥ 0.90
  Detection                Recall ≥ 0.85

### Ablation Study

Compare:

-   NLI only
-   NLI + semantic similarity
-   NLI + semantic similarity + misattribution detection
-   With source router vs. without source router
